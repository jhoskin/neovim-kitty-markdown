# Open questions: oracle parity and text metrics

- R-237: "scaled to `size - 8`" gives the same frame as mermaid-cli 12.0.0 only for a diagram that is wider than tall. For a taller diagram, mermaid-cli first limits the SVG width to `round(size * aspect)` and then reflows it to that width minus 8, so the drawn height is less than `size - 8`. The two readings give very different scores for a tall diagram. The checks accept either reading. Which one does R-237 mean?
- R-237 with R-110: the framing resamples the helper raster to `size - 8`. For diagrams with much small text, mermaid's own drawing at the helper's scale, framed the same way, stays below 0.95 against the golden, so no helper can reach the threshold through this framing. The checks then fall back to SSIM against the oracle drawn at the helper's own pixel size (mermaid-cli `--size` chosen so the drawing is exactly the helper width, as `helper/oracle/goldens.mjs` does). Should R-181 and R-237 describe that comparison instead, or name the resampling filter for the framing?
- R-181: `helper/oracle/goldens.mjs` runs the oracle with `--size` equal to the helper width plus 8 for a wide diagram (and a computed size for a tall one), then crops the golden. R-181 says `--size` is the longer side of the helper output. Should R-181 follow the script, or the script follow R-181?
- SSIM definition: "reports the mean over the image" does not say how the 11 by 11 window treats the image border (only the windows that fit inside the image, or a window at every pixel with padding). The two readings differ by more than 0.001 on small images. The checks accept either reading within 0.001.
- R-214: does the 3 px tolerance for fallback-font text apply to a whole label of any length, or per glyph? Small per-glyph differences add up on a long label. Does "text that needs a fallback font" include emoji drawn from a color emoji font? The checks apply 3 px to the whole label for both, and compare width and height for SVG and HTML labels.
